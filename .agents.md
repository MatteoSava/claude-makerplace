# Agent Operating Guide

This package is Claude Makerplace, a Claude Code marketplace with multiple organized plugins plus Codex and OpenCode compatibility adapters.

## Priorities

1. Preserve sanitization.
2. Keep skills concise and reusable.
3. Keep autoresearch focused on self-improving the skills from evidence and feedback.
4. Validate marketplace, plugin, hooks, and skill frontmatter after edits.

## Python Rules

- Use `uv` for every Python operation.
- Do not use system Python or `pip`. Use `npm`/`npx` only for OpenCode package or MCP validation where the package surface explicitly requires Node tooling.
- Keep tool versions pinned.
- After editing `.py` files, expect the Python quality hook to run:
  - Ruff check
  - Ruff format check
  - Pyright
  - Mypy
  - targeted pytest when matching tests exist

If the hook reports failures, fix them before calling the work complete.

Hook controls:

- `MAKERPLACE_HOOK_PROFILE=minimal`: Ruff lint and format check only.
- `MAKERPLACE_HOOK_PROFILE=standard`: Ruff, Pyright, Mypy, and targeted pytest.
- `MAKERPLACE_HOOK_PROFILE=strict`: standard checks plus full `tests/` pytest when present.
- `MAKERPLACE_HOOKS=off`: disable package hooks temporarily.

## Marketplace Rules

- Validate the root marketplace:

```bash
claude plugin validate .
```

- Validate the plugin:

```bash
claude plugin validate ./plugins/agentic-research
claude plugin validate ./plugins/cloud-delivery
claude plugin validate ./plugins/product-engineering
claude plugin validate ./plugins/python-quality
claude plugin validate ./plugins/agent-harness-control
claude plugin validate ./plugins/makerplace-system
```

- Validate JSON after changing manifests or hooks:

```bash
jq . .claude-plugin/marketplace.json
jq . plugins/agentic-research/.claude-plugin/plugin.json
jq . plugins/agent-harness-control/.claude-plugin/plugin.json
jq . plugins/python-quality/hooks/hooks.json
jq . plugins/makerplace-system/hooks/hooks.json
jq . plugins/repository-documentation/hooks/hooks.json
```

Codex adapters:

- Root marketplace: `.agents/plugins/marketplace.json`
- Per-plugin manifests: `plugins/*/.codex-plugin/plugin.json`
- Keep Codex marketplace entries aligned with the Claude plugin directories.
- Codex can run command hooks from plugin-local `hooks/hooks.json` when plugin hooks are enabled and trusted.
- Project-local Codex hooks live in `.codex/hooks.json` and require `.codex/config.toml` hook features.
- Keep hook behavior portable: use `type: "command"` entries, avoid async/prompt/agent hooks, and do not rely on Stop matchers.

OpenCode adapters:

- Project config: `opencode.json`
- Runtime plugin: `.opencode/plugins/claude-makerplace.js`
- Installable package: root `package.json` exports `opencode-plugin/index.js` as `@claude-makerplace/opencode-plugin`.
- Skills and commands are links back to canonical Claude plugin source files.
- Agents under `.opencode/agents` are OpenCode-native adapters; keep them small and aligned with the Claude plugin agents.
- The installable package registers skills, commands, OpenCode adapter agents, and skill-local subagents through its `config` hook. Keep package behavior validated by `scripts/validate-opencode-plugin.mjs`.

## CI/CD Rules

The package ships a GitHub Actions workflow:

```text
.github/workflows/validate.yml
```

Keep CI dependencies pinned:

- `actions/checkout@v6.0.2`
- `astral-sh/setup-uv@v8.1.0`
- `uv==0.11.11`
- Python `3.12.13`

The canonical validation command is:

```bash
./bin/makerplace-validate
```

Update this script rather than duplicating validation logic inside YAML.

## Command And Agent Rules

The plugin exposes operational entrypoints:

- `plugins/makerplace-system/commands/marketplace-health.md`
- `plugins/makerplace-system/commands/skill-evolve.md`
- `plugins/makerplace-system/commands/release-readiness.md`
- `plugins/makerplace-system/commands/feedback-makerplace.md`
- `plugins/makerplace-system/agents/marketplace-auditor.md`
- `plugins/makerplace-system/agents/skill-curator.md`
- `plugins/python-quality/agents/python-quality-reviewer.md`
- `plugins/agent-harness-control/skills/repo-sentinel/SKILL.md`
- `plugins/agent-harness-control/skills/agentops-continuity/SKILL.md`
- `plugins/product-engineering/skills/webqa-devtools/SKILL.md`

Keep command files short and action-oriented. Keep plugin agent frontmatter compatible with Claude Code plugin agents: do not use `hooks`, `mcpServers`, or `permissionMode` in plugin-shipped agents.

For multi-agent organization, keep the main agent responsible for coordination and integration. Use reviewer or auditor agents for broad read-only exploration, curator agents for narrow owned edits, and quality agents for focused validation. Do not duplicate a full workflow across agents when a skill can remain the source of truth.

If a workflow becomes repeated enough to deserve a command, add it under the relevant plugin's `commands/`. If it requires a reusable delegated review or implementation role, add it under the relevant plugin's `agents/`. Do not add components only to increase counts.

## Sanitization Rules

Do not publish:

- personal names or usernames
- local filesystem paths
- private repository names
- employer or client identifiers
- internal URLs or hostnames
- telemetry session IDs
- challenge/run IDs
- device MAC addresses
- API keys, tokens, passwords, mnemonics, or private keys

Use neutral wording such as:

- `the project`
- `the repository`
- `the benchmark`
- `the Azure DevOps organization`
- `the internal documentation tool`

## Inventory Rules

The public inventory must stay sanitized.

- Public: `docs/source-inventory.md`
- Public: `docs/source-inventory.json`
- Public: `docs/selection-map.md`
- Public: `docs/source-provenance.md`
- Public: `docs/source-provenance.json`
- Local-only: `../tools/source-inventory.local.json`
- Local-only: `../tools/source-provenance.local.json`

Regenerate with:

```bash
uv run python ../tools/inventory_skills.py
uv run python ../tools/source_provenance.py
```

Never move local-only inventory or provenance files into the marketplace package.

If timeline evidence is needed, use `source-provenance` from real source repository commits.

## Autoresearch Emphasis

When explaining this package, lead with the skill-autoresearch system. Here "autoresearch" means the agent improves the skill library itself after real usage, especially when the user points out a mistake or asks for refinement.

- `skill-autoresearch-loop`
- `agentic-experiment-loop`
- `benchmark-run-operations`
- `experiment-registry`
- `score-model-probe`
- `python-quality-gate`

Frame the primary loop as:

```text
use skill -> observe miss -> update impacted skill -> validate -> reuse better behavior
```

Use the benchmark-oriented loop only when the task is actually about scored AI experiments:

```text
baseline -> bounded variant -> measured run -> trace/score analysis -> promote or discard
```

Do not describe experiments as successful unless score, trace, and provenance evidence support that conclusion.

If a user is frustrated, points out a mistake, or asks for a refinement after a skill was used, update the impacted skill. Generalize the lesson so it helps future users and future tasks; do not hardcode the current user's private context.

## Editing Rules

- Prefer small patches.
- Keep `SKILL.md` files focused on agent behavior, not marketing prose.
- Keep `commands/` focused on invocation flows and `agents/` focused on reusable delegated roles.
- Add a new skill only when it represents a distinct reusable workflow.
- Use `skill-autoresearch-loop` when feedback should change how the skill library behaves.
- If a source skill is represented by a merge, document it in `docs/selection-map.md`.
- Update `README.md` only when the package surface changes.
